## 1. Why this overlay may override everything in Settings

Settings declares **no `<overlayable>`** at `lineage-23.2` (`docs/10b` §1), so idmap2
takes the `!defines_overlayable` branch and accepts *any* resource as long as the
overlay fulfils one of `kDefaultPolicies`:

```cpp
// frameworks/base/cmds/idmap2/libidmap2/ResourceMapping.cpp:69-75
const Result<bool> defines_overlayable = target.DefinesOverlayable();
if (!*defines_overlayable) {
    return (kDefaultPolicies & fulfilled_policies) != 0 ? Result<Unit>({}) : Error(...)
}
```

A `/product/overlay` install supplies `PRODUCT_PARTITION`, which is in that mask — so
no signature match, no `targetName`, no group name is needed. The manifest therefore
omits `android:targetName` (a non-existent name would *fail* the policy check) and
declares `hasCode="false"`.

`android:isStatic` is deliberately **absent**: the overlay is runtime-toggleable
(`su 0 cmd overlay enable org.ztos.overlay.settings`), which matters because this is a
visual experiment on the daily driver, unlike the immutable framework overlay.

Build constraint honoured throughout (`docs/10b` §3a): the overlay never references a
resource that exists only in its own package. Every value is a literal, a public
framework attr (`?android:attr/…`), or a public framework resource
(`@android:color/…`). One exception is documented and risk-flagged in §5.3 (the two
Material `card*` attrs of `SearchBarStyle_v2`).

## 5. Risks and honest limits

### 5.1 Accessibility
Every text colour is a `?android:attr/textColorPrimary/Secondary` pair, i.e. the
theme's own contrast, not an invented pair; the only literals are the tile glyph
(`#FFFFFF` on `#0050EF`, 6.2 : 1) and the card/field surfaces, which are neutral
(`#FFFFFF`, `#F2F2F2`, `#1F1F1F`, `#000000`) with unmodified text on top.
`TextAppearance.info_label` drops **bold** → `sans-serif-medium` at 12 sp: still
semibold, still ≥ 12 sp, but a real reduction in emphasis — flagged `[?]` for the
device pass.

### 5.2 Shadowed/lost items (whole-bag replacement)
- `TextAppearance.NotificationImportanceDetail` loses its `android:featureFlag`
  font variants (`styles.xml:730-737`) and `TextAppearance.SearchBar` loses
  `@*android:string/config_headlineFontFamily` — both replaced by the Metro ramp on
  purpose.
- `TextAppearance.*` styles lose their DeviceDefault parent's inherited items; the
  bags therefore set `fontFamily`, `textSize` and `textColor` explicitly. Anything the
  DeviceDefault parent added that is *not* re-set (e.g. font feature settings) is gone.

### 5.3 `SearchBarStyle_v2` — the one flagged mechanism `[?]`
The search bar's 40 dp radius is a hardcoded `cardCornerRadius` item, not a dimen, and
`cardCornerRadius`/`cardElevation` are attrs of the **Settings** package (Material
Components AAR), which a standalone overlay cannot reference. The overlay declares the
two attrs itself (`res/values/attrs.xml`), so the bag compiles with keys
`0x7f010000/0x7f010001`; the square corners need idmap2 to remap those bag keys to the
target's attrs of the same name/type.
- If it maps: the search card is square (verified only by the compiled table; needs the
  device).
- If it does not map: the two items are ignored, the card keeps 40 dp corners, **no
  crash, no inflation error**. That is why this is shipped rather than dropped.
- Two items are dropped from the bag regardless: `android:theme`
  (`@style/Theme.MaterialComponents.DayNight`) and `strokeWidth/strokeColor`
  (`@color/settingslib_materialColorOutlineVariant` are not referenceable here).
  **This does not crash and does not require a Material theme.** Proof in the same
  tree: `res/layout/card_preference_layout.xml:18` already inflates a
  `MaterialCardView` on the Settings home page with `style="@style/ContextualCardStyle"` (:28)
  and **no** `android:theme`; that style (`res/values/styles.xml:576-583`) sets only
  `cardBackgroundColor/cardCornerRadius/cardElevation/rippleColor`. So `MaterialCardView`
  renders under the plain `Theme.Settings` activity theme, exactly what
  `search_bar.xml` will get when its style loses the item. The visible field fill is
  supplied by `drawable/search_bar_selected_background.xml`, so the result does not
  depend on the M3 card default.
- Device check: `cmd overlay dump org.ztos.overlay.settings | grep -i searchbar` and a
  screenshot of Settings home.

### 5.3b Device check for the `SearchBarStyle_v2` bag-key remap (hand this to the lead)

Run after the overlay is deployed. Three steps, increasing cost; **2 is the
decisive one, 3 is the human-visible confirmation**.

```sh
# 1. Is the overlay mapped at all, and where is its idmap?
su 0 cmd overlay dump org.ztos.overlay.settings
#    expect: packageName=org.ztos.overlay.settings, targetPackageName=com.android.settings,
#            mState=STATE_ENABLED, mIsStatic=false, and an mIdmapPath= line
#            (typically /data/resource-cache/org.ztos.overlay.settings@idmap or a
#            hash-named file under /data/resource-cache/).
#    If mState is STATE_NO_IDMAP / STATE_MISSING_TARGET the question is moot: the
#    whole overlay is inert -> check `logcat -d | grep -i 'idmap2\|overlay'`.
su 0 ls -la /data/resource-cache/ | grep -i ztos        # if the path is not printed

# 2. Did the overlay's ATTR resources map? (the remap the square corners need)
su 0 /system/bin/idmap2 dump --idmap-path <mIdmapPath from step 1> > /data/local/tmp/settings-idmap.txt
su 0 grep -E 'attr/cardCornerRadius|attr/cardElevation|style/SearchBarStyle_v2' /data/local/tmp/settings-idmap.txt
#    PASS looks like two "Mapping:" rows, one per resource:
#        0x7fXXXXXX -> 0x7f050000 (style/SearchBarStyle_v2 -> style/SearchBarStyle_v2)
#        0x7fXXXXXX -> 0x7f0100NN (attr/cardCornerRadius  -> attr/cardCornerRadius)
#    MISSING attr/cardCornerRadius row  => idmap2 did not map the Material attrs we
#    declared in res/values/attrs.xml, so the bag keys stay overlay-local and the
#    search card keeps its 40dp corners (silent no-op, no crash -- REPORT §5.3).
#    Optional pre-check of the tool itself: `su 0 idmap2 --help` (the flag is
#    --idmap-path, not --idmap, at android-16.0.0_r3:
#    cmds/idmap2/idmap2/Dump.cpp:31).

# 3. Visual proof (what the lead actually judges)
#    Settings home, light and dark: the search field must be a square card with
#    flat corners. Take one screenshot per theme.
su 0 am force-stop com.android.settings   # then reopen Settings and screenshot
```

Interpretation table:

| observation | meaning |
|---|---|
| `mState=STATE_ENABLED` + both mapping rows in step 2 | remap took; square corners are expected (§5.3 first branch) |
| `mState=STATE_ENABLED` but no `attr/cardCornerRadius` row | style maps, attr keys do not; search bar stays round — drop `SearchBarStyle_v2` from the overlay as dead weight (everything else in the overlay still applies) |
| `mState=STATE_NO_IDMAP` / `STATE_MISSING_TARGET` | the overlay is inert as a whole: it is not preinstalled where idmap2 accepts it (`docs/10b` §4), not a `SearchBarStyle_v2` problem |
| corners square but field fill wrong | unrelated to idmap: look at `res/drawable-night/search_bar_selected_background.xml` |

A faster sanity check if `idmap2` is absent from the image: `su 0 cmd overlay
dump org.ztos.overlay.settings` must print a non-empty `mIdmapPath`, and Settings
home must show *any* change from §3 (e.g. cobalt dashboard tiles) — if the tiles
are cobalt but the search bar is round, the answer is "style mapped, attr keys
did not".

### 5.4 Overlay precedence
The overlay is `priority=10` and **not** static. Any later Lineage accent overlay
targeting `com.android.settings` would win; none is expected (`cmd overlay list` on the
device is the check, `[?]`).
Animated/stateful resources are untouched, so nothing depends on animation timing.

### 5.5 Not verified on device
The `idmap2` mapping itself, dark/light switching, and every visual line above are
`[E]`. Host checks cover: every name exists with a consumer, compiled values, manifest
flags, absence of dex, deterministic rebuild.
`idmap2` is not part of the host build-tools, so no `idmap2 create` was run; on device
the checks are `cmd overlay list`, `cmd overlay dump` and logcat for
`idmap2 … not allowed to overlay resource`.

## 6. What still needs code / another overlay (cannot be done from this package)

1. **Metro page header** (title + subtitle block). Not a resource: needs
   `SettingsBaseActivity.setContentView(int)` (`SettingsBaseActivity.java:220`) and
   `SettingsHomepageActivity.onCreate:252` — the LSPosed module
   (`repo/settings/header-module/`, `evidence/settings-header/`) owns it. The two
   deliverables are complementary: RRO = colours/metrics, module = the new view.
2. **Ordinary preference row height and vertical padding.** `Theme.Settings` sets
   `android:listPreferredItemHeight=72dip` (`res/values/themes.xml:35`,
   `themes_expressive.xml:30`) and the row layouts use
   `?android:attr/listPreferredItemHeightSmall` and
   `?android:attr/textAppearanceListItem` (e.g.
   `layout/preference_widget_seekbar_settings.xml:23,46`). Both are **theme attributes**,
   not resources: changing them means replacing the whole `Theme.Settings` bag (which
   would drop `preferenceTheme`, `alertDialogTheme`, `android:actionBarStyle`, … — not
   acceptable) or overlaying the SettingsLib preference layouts, which does not work
   because a layout overlay may not reference app-private drawables/strings
   (`docs/10b` §3b). → **needs the Settings theme patched, or a SettingsLib-targeted
   pass** (see §7).
3. **Section headers / category titles.** The live style is
   `@style/TextAppearance.CategoryTitle.SettingsLib`
   (`res/layout/time_zone_search_header.xml:23`); the Settings-owned
   `TextAppearance.CategoryTitle` (`styles.xml:312`) is dead — its only reference is the
   SettingsLib variant name. The definition lives in SettingsLib.
4. **Dashboard tile labels and tile layout.** `res/layout/` has no dashboard tile
   layout and `colors.xml` has no tile-text colour: both are SettingsLib
   (`settingslib_dashboard_tile*`). Only the tile *fill and glyph tint* are reachable
   from this package (§3.2).
5. **Material 3 switch / slider accent — DONE in `framework overlay v2`.**
   The switch preference is a real Material3 widget
   (`res/layout/preference_widget_switch_compat.xml:18`,
   `com.google.android.material.materialswitch.MaterialSwitch`) whose checked track is
   `?attr/colorPrimary`; `Theme.Settings` points that at
   `@*android:color/primary_device_default_settings_light`
   (`res/values/themes.xml:68,188,249`) and the night theme at
   `@*android:color/primary_device_default_settings`
   (`res/values-night/themes.xml:21`). `repo/overlay/framework` now overrides both
   (see `evidence/framework-rro/REPORT.md` §3b/§3c), plus the M3 roles
   `system_primary_*`/`system_on_primary_*` and the `system_accent2_*`/`system_accent3_*`
   seeds — so the switch (and any M3 Slider) is cobalt. Note `_dark` does not exist at
   API 36; the dark value is the plain `primary_device_default_settings`.
   Side effect flagged there: Settings' app bar and the `?android:attr/colorPrimary`
   dashboard icons take the same accent.
6. **Page background** of Settings home (`Theme.Settings.Home`:
   `android:colorBackground=@color/settingslib_materialColorSurfaceContainerLow`,
   `res/values/themes.xml:207`) — a SettingsLib colour. Reached only through a theme
   bag or a SettingsLib overlay.
7. **Search bar row height.** `android:minHeight="72dp"` is hardcoded on
   `@+id/search_action_bar` (`res/layout/search_bar.xml:28`) — a layout value; the
   layout also references `@drawable/ic_homepage_search` and `@string/homepage_search`,
   so it cannot be overlaid safely (§3b). → needs the code hook to set a LayoutParams
   minimum, or a SettingsLib-side change.
8. **List divider colour.** `android:divider=@*android:drawable/list_divider_material`
   (`styles_preference.xml:62`, `themes.xml:222,224`) is a **framework** drawable;
   Settings defines no divider colour of its own. → framework overlay, if wanted. Metro
   lists are divider-less, and §3.4 already makes the row background uniform, so this is
   optional.
9. **Segoe typography.** No font files are shipped, so titles are
   `sans-serif-light`. Family substitution is the font-module deliverable
   (`evidence/font-module/`).
10. **Toolbar title/subtitle appearance.** `Widget.ActionBar` in Settings sets only
    `contentInsetStart` (`styles.xml:19-30`); the title text appearance comes from the
    framework DeviceDefault ActionBar styles plus SettingsLib's collapsing toolbar. →
    framework overlay (`TextAppearance.DeviceDefault.Widget.ActionBar.*`) or the
    header module.
