## 2. Exact insertion logic

### 2.1 Sub-screens and `SettingsActivity`'s home (`content_frame`)

`SettingsBaseActivity.setContentView(int)` first calls `parent.removeAllViews()` and then
inflates the screen into `content_frame`, so after the hook returns the frame has exactly
one child: `settings_main_prefs` (a `match_parent` LinearLayout that includes
`main_content` with `layout_weight=1`).

The module then:

1. removes any direct child tagged `ztmetro_header` (idempotency across recreation),
2. inflates a fresh header from the module resources,
3. inserts it **at index 0** of `content_frame` with
   `FrameLayout.LayoutParams(MATCH_PARENT, @dimen/metro_header_height /*56dp*/)`,
4. sets `topMargin = 56dp` on every other direct child.

Why step 4: `content_frame` is a `FrameLayout` and the screen layout is a `match_parent`
child; index 0 alone would be painted *behind* it (FrameLayout z-order) and be invisible.
The header is still child #0 as specified; the screen layout is shortened by exactly the
header height through its FrameLayout margin. **The header is never inserted into
`settings_main_prefs`**, so `main_content`'s `layout_weight=1`, the switch bar, the
fragment container and the fragment's own `match_parent` behaviour are untouched: the
weight is resolved inside the LinearLayout, which still gets the remaining height.

If the parent is not a FrameLayout (defensive, not the case in `lineage-23.2`), the module
uses `LinearLayout.LayoutParams` for a LinearLayout and plain `ViewGroup.LayoutParams`
otherwise, so `addView` can never throw `ClassCastException`.

### 2.2 Home

`SettingsHomepageActivity.onCreate` calls `setContentView` at line 252 and then builds the
homepage; the hook runs after the whole method, so `homepage_container` exists. The header
is inserted at **index 0 of `homepage_container`** (Vertical LinearLayout inside the
NestedScrollView): it becomes the first scrolling block, above `suggestion_content`. The
container's `-8dp` top margin is compensated on the header's own `topMargin` so the first
8 dp are not clipped.

### 2.3 Title and subtitle

| field | value |
|---|---|
| title | `activity.getTitle()` (already the per-screen breadcrumb) |
| subtitle | last back-stack entry whose `getBreadCrumbTitle()` differs from the title; otherwise the module string `@string/metro_header_subtitle_static` = `ztMetro` |

The back stack is read by reflection (`getSupportFragmentManager` →
`getBackStackEntryCount` → `getBackStackEntryAt(i).getBreadCrumbTitle()`), so the module
needs no `androidx.fragment` compile dependency and a renamed method can only cost the
subtitle. Refresh happens on attach, after `setTitle(...)` (back-stack drill-down) and on
`onResume`.

### 2.4 Look

All values come from `res/values/metro_header_{colors,dimens,styles}.xml`, generated by
`tools/gen_header_res.py` from `design/tokens/ztmetro.tokens.json` (no colour/size is
written twice; Java only reads resource ids):

- background `@color/metro_header_bg` = **#0050EF** (`color.accent.base`), a module-owned
  `<shape>` drawable (a *new* drawable: legal because it is inflated from the module APK),
- title 24sp, `sans-serif-light` (derived: token `type.header.title_size_sp` 48 / 2),
- subtitle 12sp, `sans-serif`, colour **#B3FFFFFF** = 70 % of `color.accent.foreground_on_accent`
  (12sp is exactly `type.ramp[caption]`),
- height 56dp (`2 × metrics.status_strip_height_dp` 28), side padding 16dp
  (`metrics.page_margin_dp`).

## 3. Resource inflation — the main technical risk, and how it is solved

The header's layout/drawable/style/dimens exist only in the module APK. Inside the
Settings process the module is a bare dex; Settings' own `Resources` must never be asked
for `R.layout.metro_header`. The module therefore obtains the **module's** `Resources`
and inflates with it:

1. **package-context** (preferred, public API):
   `createPackageContext("org.ztmetro.settingsheader", CONTEXT_INCLUDE_CODE | CONTEXT_IGNORE_SECURITY).getResources()`.
2. **package-resources** (public API, no Context/code):
   `PackageManager.getResourcesForApplication("org.ztmetro.settingsheader")`.
3. **asset-manager** (hidden API, classic Xposed fallback):
   `AssetManager#addAssetPath(<module base.apk>)` + `new Resources(assets, hostDisplayMetrics, hostConfig)`.
   It is isolated from Settings' resource table, so it cannot pollute Settings' ids.

Every path is validated by looking up `layout/metro_header` + the module package in the
result; the first hit wins and is logged once:

```
I ztmetro-header: module resources via package-context   (or package-resources / asset-manager)
```

The chosen `Resources` is wrapped in a private `ModuleContext extends ContextWrapper`
(overrides `getResources`, `getAssets`, `getTheme`, `getClassLoader`) and the inflater is
`LayoutInflater.from(activity).cloneInContext(moduleContext)`. A module-only theme is
created with `Resources.newTheme()`; the host theme is deliberately **not** copied into
it, because it was built by a different `AssetManager` and its Settings `0x7f…` style ids
could accidentally resolve against the module's `0x7f…` ids.

Evidence that the approach is legal and compiles into a self-contained APK
(`logs/build-verify.txt`):

- `aapt2 dump resources` shows the module's own namespace (`0x7f…`) carrying
  `color/metro_header_bg` = `#ff0050ef`, `color/metro_header_subtitle` = `#b3ffffff`,
  `dimen/metro_header_height` = `56dp`, `dimen/metro_header_title_size` = `24sp`,
  `dimen/metro_header_subtitle_size` = `12sp`, `drawable/metro_header_bg`,
  `layout/metro_header`, `string/metro_header_subtitle_static` = `"ztMetro"`;
- `aapt2 dump xmltree res/layout/metro_header.xml` shows the header, its `#ztmetro_header`
  tag, the style references and both `TextView`s;
- `dexdump` lists `SettingsHeaderHooks`, its four anonymous `afterHookedMethod` overrides,
  `HeaderBinder`, `HeaderResources`, `HeaderTitles`, `HeaderViewFactory`, `ModuleContext`,
  `ModuleEntry`, and the dex string pool contains `setContentView`, `setTitle`, `onResume`,
  `onCreate`, `com.android.settings.core.SettingsBaseActivity`,
  `com.android.settings.homepage.SettingsHomepageActivity`;
- `apksigner verify` passes (APK Signature Scheme v3, valid for Android 9+ / API 36).

Why this cannot crash Settings: every hook body is inside `try { … } catch (Throwable)`
with `XposedBridge.log`; hook *installation* is per-hook guarded; `HeaderResources.get`
returns null-equivalent failure by throwing and is only called from inside the guarded
hook; the view hierarchy mutations are plain `addView`/`setLayoutParams` on views that
were just resolved, and the binder returns early when the container/header/layout is
missing. The module has no Activity, Service, Receiver, permission or `Application` class,
so it cannot change Settings behaviour outside these four hooks. With the module disabled
or the hooks missing, Settings is bit-for-bit stock (the hooks only *add* a view after the
stock method ran).

## 4. Build

```sh
repo/scripts/build-header-module.sh
```

- downloads (once) the **official Xposed Maven repository** artifact
  `de.robv.android.xposed:api:82` —
  `https://api.xposed.info/de/robv/android/xposed/api/82/api-82.jar`,
  sha256 `f48c635f1c7469fdec0e00ad2ea0b7a6b2f5b55065784a35b7ca3a84615e8e25` — into the
  gitignored `<module>/build/deps/`; it is compile-only and never packaged;
- regenerates the res/values from the token JSON (`--check` mode available),
- `aapt2 compile` + `aapt2 link` (`-A assets`, min 29, target 36), `javac --release 11`,
  `d8 --min-api 29`, `zipalign -p 4`, `apksigner sign` (dev keystore generated on first
  run),
- verifies signature, badging, `assets/xposed_init`, xposed meta-data, module resources
  and hook strings in `classes.dex`, then prints path/size/sha256 and writes
  `build/verify.txt`.

`assets/xposed_init` contains `org.ztmetro.settingsheader.ModuleEntry` — required for
LSPosed's legacy module entry point; without it the manager shows the module but never
loads the hook class.

Xposed API / minimum: the artifact above is the last published `de.robv.android.xposed`
API (level **82**).  The manifest declares `xposedminversion=93` — the level LSPosed's
module documentation requires for legacy modules; LSPosed and the Android-16-capable
Vector fork (LSPosed v1.10.2+) report an API level >= 93 to legacy modules, so the check
passes.  The module only calls API-82 surface (hookMethod / log / findClass).

## 5. Install / enable (Magisk + LSPosed)

1. Install the APK as a normal user app:
   `adb install -r repo/evidence/settings-header/ztmetro-settings-header.apk`
   (or copy it to the phone and tap it).
2. Magisk app → Modules → install/enable **LSPosed** (Zygisk), reboot. Android 16 needs
   LSPosed **v1.10.2+** (JingMatrix/Vector) — older LSPosed does not inject on API 36.
3. Open LSPosed Manager → **Modules** → *ztMetro Settings header* → enable it.
4. Set its scope to **com.android.settings only** (the module ships
   `xposedscope = com.android.settings`; verify the checkbox and do not add SystemUI).
5. Force-stop Settings so the hook loads in a fresh process:
   `adb shell am force-stop com.android.settings`, then open Settings.
   (LSPosed may offer "force stop" from the module page.)
6. Confirm loading:
   `adb logcat -s ztmetro-header` should show
   `loading in Settings (xposed API 93)` and
   `module resources via package-context` (or `package-resources` / `asset-manager`).

### Rollback

- Disable the module in LSPosed Manager and force-stop Settings — no reboot needed; the
  hook is not installed in a fresh process.
- Or uninstall the APK (`adb uninstall org.ztmetro.settingsheader`).
- Nothing else is modified: no overlay, no patched APK, no Settings data.

## 7. Open risks

1. **No on-device run yet.** The resource path, insertion and hooks are compile- and
   package-verified, but not executed under LSPosed. The first device step must read the
   `ztmetro-header` log lines above; if `createPackageContext` is refused, the module
   automatically falls back to `getResourcesForApplication`/`AssetManager` (both compiled
   in) and the same log names the winner.
2. **Homepage geometry.** `homepage_container` scrolls under an AppBar with a custom
   `HomepageAppBarScrollingViewBehavior`; the header may visually interact with the search
   bar at scroll position 0. The `-8dp` container margin is compensated, but only a
   screenshot can confirm the final offset.
3. **Font scale.** The header is a fixed 56dp (spec); at large font scale the 24sp/12sp
   block can clip its subtitle. Making the height `wrap_content` with `minHeight=56dp`
   would fix it at the cost of exact spec height — decide after the visual check.
4. **`setContentView(View)` overloads are not hooked** (the requirement names the `int`
   overload). A screen that replaces content through the `View` overload would add an
   un-offset view after the header; no such path is used by the stock flows checked
   (createUiFromIntent uses the int overload).
5. **Hidden API.** The `AssetManager` fallback uses `addAssetPath` (public `@hide`).
   Settings is platform-signed and LSPosed injects with hidden-API access, so it is
   expected to work; the public paths are tried first, so this only matters if both public
   paths fail.
6. **LSPosed/Vector forks.** `xposedminversion=93` matches LSPosed/Vector legacy
   behaviour; a fork that advertises a different legacy level would refuse the module
   (visible in LSPosed's log, module simply inactive — Settings unaffected).
7. **Dev signing key** is generated locally on first build and is not committed; rebuilds
   on a fresh build dir produce a new certificate, which is fine for personal use but
   means Play/updating across machines is not signature-stable.
